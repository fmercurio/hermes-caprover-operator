# Historical operation cards

CapRover Operator returns an HTML card with a saved plan or receipt. It is a product feature, generated by the native plugin from the same result returned to Hermes. It is not a separate dashboard or a video overlay. Doctor remains read-only and does not create a card or a ledger.

The card shows the configured app and origin, baseline and requested images, a dated status, native approval requirement, a durable attempt marker when recorded, separate metadata/runtime/HTTP evidence, and the manual next step. Short image references are display-only; expand **Plan details & full image references** and select a full reference to copy it. This needs no script or clipboard permission.

## Public Hermes integration

The adapter returns `presentation.cards[]`, where each item contains:

```json
{
  "available": true,
  "file": "/absolute/private/plugin-data/caprover-operator/cards/<sha256>.html",
  "preview": "::preview{file=\"/absolute/private/plugin-data/caprover-operator/cards/<sha256>.html\"}",
  "card": {"schema": 1, "historical": true}
}
```

The actual `card` contains the bounded facts as JSON, including full image references. Every non-doctor tool description tells Hermes to emit each available `preview` string unchanged, on its own line. For example, the assistant's rendered response contains this standalone paragraph, outside a code fence:

```text
::preview{file="/absolute/private/plugin-data/caprover-operator/cards/<sha256>.html"}
```

This uses the documented core [inline preview directive](https://hermes-agent.nousresearch.com/docs/developer-guide/desktop-plugin-sdk). Its implementation exists in the minimum supported Hermes v0.22.6: [InlinePreviewDirective at f0d9488](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/apps/desktop/src/components/assistant-ui/inline-preview-directive.tsx) and the [core contribution registration](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/apps/desktop/src/app/contrib/controller.tsx). No private frontend imports, core patches, desktop bundle, backend route, or `provides_ui` declaration is required: the public core renderer owns the preview.

Desktop renders a local HTML file inline in an opaque-origin frame. Hermes supplies its sizing/theme bridge. The card itself contains no JavaScript, external assets, network requests, links, forms, execution controls, or `data-hermes-send` actions. Its content policy blocks network/asset loads, but permits Hermes's injected inline sizing script. Remote gateways without local file access may fall back to the standard preview attachment. A model must emit the directive to place the full card in the conversation; its inclusion is not an automatic replacement of a tool-result bubble. JSON facts and the ordinary operation result remain usable in CLI and unsupported clients.

## Evidence and storage boundaries

- Every card is explicitly a **historical snapshot**, not ongoing availability. The observed time comes from the receipt; missing evidence stays missing.
- HTTP 200 and updated image metadata cannot turn an unproven runtime into a verified rollout. An inconsistent verified receipt is displayed as incomplete evidence.
- Native approval is required for every apply, but the ledger does not separately persist the approval event. The card says so instead of fabricating an approval badge.
- A durable attempt marker is written before a possible POST. It does not prove delivery to CapRover or establish a count of server requests. Cards do not claim either.
- The rendering function selects fields; it excludes raw logs, runtime task payloads, credentials, environment data and state fingerprints. All displayed text is HTML-escaped and bounded.
- The export creates only immutable presentation files. It never opens the client or ledger, refreshes evidence, grants approval, retries an operation, or rolls back. History export is bounded to five cards and excludes receipts outside the current configured app/origin.
- The existing profile data directory and `cards/` must be owned by the user and mode `0700`. Files are mode `0600`. Paths are fixed from the adapter binding, directory traversal follows no symlinks, and published filenames are the SHA-256 of the HTML. Existing files are verified, never overwritten. Changed evidence creates a different file; repeated evidence reuses the file. Snapshots remain until the owner removes them and can include internal app/image/origin identifiers.
- Export failure cannot turn a completed operation into an error. The original result and JSON card remain available where possible; presentation failure is never grounds to repeat apply.

## Reproducible visual fixtures

From the plugin checkout:

```sh
python scripts/preview_operation_cards.py /private/tmp/caprover-card-fixtures > /private/tmp/caprover-card-fixtures.json
```

The output manifest explicitly marks five scenarios as synthetic: planned, uncertain, metadata with HTTP but no runtime proof, unhealthy, and verified. It contains real generated file paths and the exact preview directives. These fixtures validate layout only; they are not deployment proof. In a disposable local Hermes Desktop/Webapp session, have the assistant emit one returned directive on its own line and verify the card renders in the conversation. Expanding the full-image section must reveal both complete digests without causing a tool call or network request.

For native end-to-end evidence, use the normal Hermes tools against the isolated CapRover lab. Preserve their `presentation.cards[].file` files with the native tool-result/receipt before cleaning up the temporary profile. Record the actual Hermes version and distinguish real app/HTTP evidence from fixture screenshots.

Behavioral tests cover weaker versus stronger evidence, expired plans, omitted private fields, escaped markup, no action/network elements, immutable private files, tampering/symlink refusal, history bounds, unchanged ledger bytes, and a renderer exception after an authorized apply that preserves its result without a second apply.
